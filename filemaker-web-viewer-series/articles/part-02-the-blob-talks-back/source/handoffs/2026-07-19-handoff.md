## Where Article Two Starts

Article One ends with the Web Viewer being read-only:

```text
FileMaker -> Web Viewer
```

Article Two picks up naturally from that point. The new lesson is not that FileMaker can run JavaScript, and not that JavaScript can call FileMaker. Both have been true for a long time; please do not write the article as if we have just found fire.

The lesson is the ownership contract:

- FileMaker sends context into the Web Viewer.
- JavaScript renders that context.
- JavaScript can report user intent back to FileMaker.
- FileMaker decides what that intent means.

Do not let the Web Viewer become the application owner. Article Two is about action envelopes, not browser code rummaging through authority because it found a convenient API.

The article should pick up directly from Article One's takeaway:

> Next, the viewer stops being read-only. The ownership boundary stays the whole game; everything else is just better lighting.

The body should teach, in order:

1. **Why one-way context was not enough**
   - Article One proved FileMaker can assemble the package and push context.
   - Article Two adds the return trip.
   - The return trip should report intent, not mutate FileMaker state directly.

2. **Action envelopes**
   - Define an action envelope as a small JSON object sent from JavaScript to FileMaker.
   - The envelope should contain at least `type`, `payload`, and viewer/framework metadata.
   - The envelope is boring by design. Boring contracts are easier to debug; exciting contracts are how integrations become oral tradition.

3. **The JavaScript bridge**
   - Introduce a small Web Viewer action API, probably in a new module:
     - index `25`
     - name `wv.platform.actions.js`
   - The API should expose a function like:

```js
WV.sendAction(type, payload, options)
```

   - That function should build the JSON envelope and call FileMaker through `FileMaker.PerformScript(...)`.

4. **The FileMaker action handler**
   - Add a FileMaker script such as:
     - `WV__Demo_Handle_Action`
   - It receives raw JSON from the Web Viewer.
   - It validates the payload.
   - It writes the action JSON into visible demo fields.
   - It updates status/action count.
   - It may push an acknowledgement context back to the already-loaded viewer.

5. **A small visible action demo**
   - Keep the same context-card renderer from Article One.
   - Add one or two Web Viewer buttons that send action envelopes:
     - `demo.inspect_context`
     - `demo.mark_movie`
   - These should not update production movie records.
   - The visible result should be FileMaker fields changing outside the Web Viewer, plus an optional acknowledgement rendered back inside the viewer.

6. **Walkthrough**
   - Load the viewer.
   - Build/push context.
   - Click a Web Viewer action button.
   - Inspect the FileMaker action JSON field.
   - Confirm FileMaker, not JavaScript, owns the resulting state.

7. **Debugging contract**
   - If the action button does nothing, check whether the Web Viewer is actually loaded in FileMaker, not a browser harness.
   - If the handler receives bad JSON, inspect the action envelope before changing renderer code.
   - If FileMaker state changes but the viewer does not show acknowledgement, check push context, not the action send path.

8. **Look forward**
   - Article Three will use real FileMaker records and a richer renderer, moving toward the Flicks ranked-list surface.
   - Do not introduce the ranked-list renderer in Article Two.
   - Do not introduce smart `ensure loaded` as the main demo path yet. It may be mentioned as a future convenience, but Article Two should keep the load/push/action flow visible.


### 8. Add A JavaScript Action Module

Add a new `LIBRARY_CODE` record:

| Index | Name | Purpose |
| ---: | --- | --- |
| `25` | `wv.platform.actions.js` | Builds action envelopes and sends them to FileMaker. |

Use a standard module header matching the Article One pattern.

The module should expose a small API:

```js
WV.sendAction = function (type, payload, options) {
  // build envelope
  // call FileMaker.PerformScript(...)
  // return "ok", "noFileMaker", or "err"
};
```

Recommended envelope shape:

```json
{
  "__wv_action": {
    "version": 1,
    "source": "wv.platform.actions",
    "ts": "client timestamp if useful"
  },
  "type": "demo.mark_movie",
  "payload": {
    "movie_id": "...",
    "genre_id": "..."
  }
}
```

Recommended FileMaker target script:

`WV__Demo_Handle_Action`

Use `FileMaker.PerformScript("WV__Demo_Handle_Action", JSON.stringify(envelope))`.

Guard for non-FileMaker execution:

- if `window.FileMaker` is missing
- or `FileMaker.PerformScript` is not a function

Return a clear result such as `noFileMaker`, not a vague shrug dressed as success.
