## Where This Pass Starts

The completed two-way demo established this contract:

```text
FileMaker context
  -> Web Viewer render
  -> JavaScript action envelope
  -> FileMaker handler
  -> FileMaker acknowledgement context
```

The next job is not to invent another bridge. The job is to give the existing bridge real FileMaker records to carry and something more useful to render.

The reader should be able to follow three related objects without confusing them:

1. Native FileMaker records and found-set/filter state.
2. The JSON payload FileMaker deliberately shapes for the viewer.
3. The ranked rows JavaScript renders from that payload.

The action envelope from the previous pass comes with us. A row selection or filter change may report intent through `WV.sendAction`; FileMaker remains responsible for deciding which record is selected and which context comes back.

## Methodology Before Demonstration

The ranked list is a teaching surface, not the subject of the article. Use it to make the reusable method visible:

1. FileMaker shapes native data into an explicit contract.
2. Named Web Viewer modules render that contract.
3. JavaScript reports narrow user intent through the established bridge.
4. FileMaker validates the request against current application state, performs the native work, and returns authoritative context.
5. The same explicit boundaries support layered debugging and give AI-assisted code a constrained, reviewable place to land.

The article should explain the ranked-list implementation only as far as the reader needs to follow that method. Exact schema references, module indexes, complete calculations, handler steps, and loading parameters belong in the build instructions and source exports when they do not advance the published argument. Concrete native screenshots and representative source-backed excerpts remain necessary evidence.

## Editorial Job

Move from scalar demo defaults to native FileMaker record data. Use a ranked-list surface to teach how FileMaker-owned data shaping, modular rendering, narrow return actions, layered diagnosis, and constrained AI assistance work together without moving query, privilege, relationship, selection, or application-state rules into JavaScript.

The body should teach, in dependency order:

1. **What changed since the last round**
   - The transport and ownership contract already work.
   - This pass changes the weight and shape of the context.
   - The viewer receives a record collection instead of a few scalar defaults.

2. **Define the ranked-view job before showing code**
   - Explain what the reader will see.
   - Identify which values are display facts, stable identity, order/rank, filter context, and selected state.
   - Do not let the visual design silently become the data contract.
   - State plainly that the ranked list is the example used to exercise the method, not a ranked-list design lesson.

3. **Native data shaping belongs in FileMaker**
   - FileMaker establishes a native found set that remains inspectable in the demo.
   - FileMaker chooses records and applies find, relationship, and privilege rules.
   - FileMaker emits only the fields the renderer needs.
   - JavaScript does not query FileMaker tables or reconstruct business rules from labels.
   - In the article, abridge query and loop mechanics once the FileMaker ownership boundary is proven; retain the exact calculations in the build materials.

4. **The ranked-view JSON contract**
   - Use stable record ids.
   - Include display-ready title/year or equivalent source-backed values.
   - Include explicit rank/order values.
   - Include FileMaker-owned selected state.
   - Include only filter and summary metadata the renderer actually consumes.
   - Preserve the existing framework and action-acknowledgement metadata where it still applies.

5. **The ranked-list page and renderer**
   - Introduce only the modules required by the verified dependency closure.
   - Render empty, loading, populated, and selected states from one contract.
   - Keep repeated-row rendering in JavaScript and data selection in FileMaker.
   - Teach why named modules and declared dependencies make code reviewable; do not make the reader memorize the demo's module inventory.

6. **Reuse the action bridge**
   - A row click or filter control calls `WV.sendAction`.
   - The action payload carries stable ids, not display labels pretending to be ids.
   - FileMaker validates the row id against the current ranked collection.
   - FileMaker navigates to the corresponding native movie record within the ranked found set, rebuilds context, and pushes acknowledgement.
   - The demo layout makes the native current record and found-set position visible; a global id alone is not sufficient evidence of the return trip.
   - Move quickly past bridge mechanics established last round. The new lesson is FileMaker performing visible native work before it returns state.

7. **Loading becomes just smart enough**
   - Introduce `ensure loaded` only if the richer renderer makes unconditional reloads visibly wasteful.
   - Keep the fallback and cache state inspectable.
   - Do not teach the final production cache/version contract here; that belongs in `Cache Me If You Can`.

8. **Walk through the native-data path**
   - establish and visibly inspect the native found set
   - build the ranked-view JSON
   - load or ensure the correct viewer package
   - push context
   - select a Web Viewer row
   - observe FileMaker navigate to the corresponding native record
   - inspect the outgoing action and returned FileMaker-owned selection

9. **Debug the layers separately**
   - native found set or relationship
   - native current-record navigation
   - FileMaker JSON shaping
   - module assembly and loading
   - repeated-row rendering
   - action payload ids
   - selected-state acknowledgement
   - Use the demo's exact fields and status values as evidence, but organize the prose around the reusable diagnostic boundaries.

10. **Keep the AI provenance visible but brief**
    - State early that AI assisted with renderer development or revision.
    - Identify the human-owned payload and action contracts.
    - Reserve the full prompt/review/native-test loop for `The Prompt Thickens`, where it will be used to build the visual payoff: a richer Web Viewer visualization coordinated bidirectionally with a native FileMaker list.
    - Describe the renderer brief in terms of input, output, authority, presentation states, and allowed module boundaries rather than treating generated code volume as the achievement.

11. **Stop at the right boundary**
    - The demo may change global demo selection/filter fields.
    - It should not broadly mutate production movie, genre, rating, or ranking records.
    - A realistic renderer is not yet a production deployment pattern.

The ranked list is deliberately the contract-teaching surface, not the visual ceiling. Do not pull the hybrid native-list/Web-Viewer visualization forward into this installment; close by making its role in the next pass clear.

## Action And Ownership Contract

Reuse `WV.sendAction`. Do not add direct `FileMaker.PerformScript` calls to ranked-row click handlers.

Keep the action vocabulary small. After inspecting the production source and the teaching needs, choose only the row-selection or filter actions required by the walkthrough.

For every action:

1. JavaScript reports intent and stable ids.
2. FileMaker validates envelope version, source, action type, and payload.
3. FileMaker decides whether the requested record/filter is valid in current context.
4. FileMaker updates only the intended demo state.
5. FileMaker rebuilds and pushes context when the viewer must reflect the result.

Do not let JavaScript's local row highlight become authoritative selection. It may provide immediate affordance while a click is in flight, but acknowledged selection comes from FileMaker context.
