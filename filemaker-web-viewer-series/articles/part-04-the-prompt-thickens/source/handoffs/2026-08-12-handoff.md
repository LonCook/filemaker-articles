## Post-Build Architecture Reconciliation — 19 Aug 2026

The implementation history changed the exact meaning of “native FileMaker list.” The final hybrid layout does not use a `MOVIE`-based List View or navigate a native found set during chart interaction.

The accepted structure is:

- `WV Framework - Hybrid` is based on the one-record `SOLUTION__all` table occurrence;
- `wv_main` remains resident on that stable host;
- ranked movies appear in the native `portal.hybrid_movies` portal, based on `MOVIE_GLOBAL_RATING`;
- `SOLUTION__all::g_wv_hybrid_movie_ids` owns the ordered portal membership list;
- `FOCUS::g_wv_demo_movie_id` owns acknowledged selection;
- the rating globals own the acknowledged band;
- portal row selection and Web Viewer actions both patch that FileMaker state, then push acknowledgement context without navigating the host record or refreshing the Web Viewer.

The earlier List View, ROWID, `Go to List of Records`, timer, and viewer-recovery paths remain part of the authentic diagnosis and revision story. They are superseded implementation attempts, not the final build target. Read “native FileMaker list” below as the native portal list unless a passage is explicitly describing one of those failed attempts.

## Where This Pass Starts

The cumulative demo already proves this path:

```text
FileMaker records and current native state
  -> documented context JSON
  -> named Web Viewer modules
  -> rendered ranked rows
  -> WV.sendAction with stable-id intent
```

This pass does not need another bridge. It needs a payoff worthy of the bridge already built.

The visible result should be a hybrid interface: a native FileMaker list and a richer Web Viewer visualization acting on the same FileMaker-owned selection and filter state. A choice made in either surface should become native FileMaker state, then return to both surfaces through the established contracts.

The visualization is still a teaching surface. This time it should also make an honest case for using a Web Viewer.

## Editorial Job

Make the AI-assisted development process visible and reviewable while building the full interface promised last round. The article should show a FileMaker developer doing the work that remains human-owned: defining the behavior, supplying the relevant context, constraining the change, reviewing the proposal, testing it in FileMaker, recording the failure, and using that evidence to request a narrower revision.

The article is not a survey of prompting techniques. It follows one real change from brief to verified result.

Teach the work in dependency order:

1. **Define the payoff before prompting**
   - A native FileMaker list and a richer Web Viewer visualization behave as one interface.
   - FileMaker owns the selected movie, active filter or rating band, native found set, and acknowledged result.
   - The Web Viewer supplies the visual analysis and interaction that the native list does not readily provide.

2. **Write the human-owned brief**
   - State the visible behavior of both surfaces.
   - Identify the existing modules and FileMaker scripts the change may touch.
   - Define the input context, allowed return actions, ownership boundary, loading and empty states, and acceptance tests.
   - State what JavaScript is not allowed to own.

3. **Supply relevant context to the AI**
   - Current module headers and exact source.
   - Representative JSON copied from the working demo.
   - Relevant FileMaker script contracts and native-list behavior.
   - Module dependency information.
   - Native screenshots and any failure evidence.
   - Explicit stop lines.

4. **Review the first output as a proposed change**
   - Check payload and action-contract compliance.
   - Check dependency declarations and loading order.
   - Find invented fields, scripts, APIs, and assumptions.
   - Reject direct `FileMaker.PerformScript` calls in visualization code; the established public bridge is `WV.sendAction`.
   - Reject browser-owned authoritative selection or filters.
   - Reject synthetic production-looking data and decorative interactions that cannot complete the FileMaker round trip.
   - Keep the useful code. The first output is a proposal, not a small coronation.

5. **Integrate and test in the right environments**
   - Use a browser harness for quick renderer layout and interaction inspection where useful.
   - Use the native FileMaker file for the actual list, Web Viewer bridge, context, action, layout, acknowledgement, and record-state proof.
   - A browser screenshot proves the browser harness can take screenshots. It does not prove the FileMaker interface works.

6. **Turn failure into the next prompt**
   - Capture the observed failure, expected behavior, incoming context, outgoing action, native FileMaker state, and relevant source.
   - Diagnose the failed layer before revising.
   - Constrain the next prompt with that evidence. Do not replace diagnosis with `try again`.

7. **Prove the final two-way interface**
   - Native list selection updates FileMaker state and the visualization.
   - Visualization focus selection sends stable-id intent through `WV.sendAction`; FileMaker validates it, updates the native selection, and returns acknowledgement context.
   - A visualization filter or rating-band interaction sends a narrow request; FileMaker applies the authoritative filter or found-set change and refreshes both surfaces.
   - Both surfaces settle on the same FileMaker-owned state.

8. **Name the human decisions that remain**
   - Purpose of the visualization.
   - Data and action contracts.
   - State ownership.
   - Authorization and record effects.
   - Acceptance of production risk.
   - Whether generated code belongs in the maintained system.

9. **Hand off the production concerns**
   - This pass may use only the loading behavior the interface needs.
   - Dirty/version tokens, final cache rebuilding, loaded-viewer maps, bounded retry, deployment, and rollback belong in `Cache Me If You Can`.

## State And Interaction Contract

The final exact JSON and action names must come from the verified demo design. The method is fixed:

1. FileMaker establishes the native list's records, selection, and active filter or rating band.
2. FileMaker shapes the visualization context from that authoritative state.
3. JavaScript renders the chart and reports narrow user intent through `WV.sendAction`.
4. FileMaker validates the request against the current context and available native records.
5. FileMaker changes the native selection, found set, or filter state.
6. FileMaker refreshes the native list as needed and pushes acknowledgement context.
7. The native list and visualization redraw from the returned FileMaker state.

Keep the action vocabulary limited to the visible walkthrough. A movie-selection action and a meaningful visual filter or band action are enough if they prove both directions. Do not import the production dashboard's entire action vocabulary simply because it is already spelled correctly.

The Web Viewer may retain transient hover, animation, or in-flight presentation state. It may not retain authoritative selected-movie, native found-set, or filter state that contradicts FileMaker.
